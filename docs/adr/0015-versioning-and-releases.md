# ADR 0015: Versioning with GitVersion, and a release for every merge to main

- Status: accepted
- Date: 2026-10-03
- Issues: #162, #43, #258, #259
- Builds on: [ADR 0014](0014-server-and-container.md)

## Context

Ariadne needs one version, without anyone editing a number by hand, for the container image, the GitHub release and
later the npm packages and the VS Code extension. The other GravionLabs repositories use GitVersion through the shared
actions in `GravionLabs/ci`; Ariadne does the same.

## Decision

- **`GitVersion.yml`** has `mode: ContinuousDeployment` and `next-version: 1.0.0`. The first release is 1.0.0; each
  later release on `main` counts the patch up from the last `vX.Y.Z` tag. `+semver: minor` or `+semver: major` in a
  commit message bumps that part. Checked on a copy of the repository: 1.0.0, then 1.0.1 after a `fix`, then 1.1.0
  after a commit with `+semver: minor`.
- **Every merge to `main` that passes the checks is a release.** The `release` job in `ci.yml` waits for the lint, build
  and test job, the format job and the C# compile job, runs on `main` only, and calls the shared
  `docker-package.yml` workflow. That workflow determines the version, lints the Dockerfile, publishes the image to
  `ghcr.io/gravionlabs/ariadne` for `linux/amd64` and `linux/arm64` with the tags `latest`, `1`, `1.0` and `1.0.0`, and
  creates the GitHub release `v1.0.0` (and the tag) with notes generated by git-cliff from the Conventional Commits
  (`cliff.toml`).
- **Pull requests do not release.** The `Container` workflow builds the image and checks that it starts and serves the
  app when a pull request touches anything that goes into it.
- **The image is built once.** The build stage runs on the build machine (`--platform=$BUILDPLATFORM`), because the
  output is plain JavaScript; only the Node binary is taken for the target platform. The arm64 image is therefore not
  built under emulation, apart from one `apk add`.
- **Commits are Conventional Commits**, and a squash merge keeps the pull request title, so the title decides the
  entry in the release notes: `feat:` and `fix:` are listed, `chore:`, `ci:`, `test:` and `build:` are not.

## Consequences

- `main` should receive finished work. Epics land as one or a few pull requests, as the epic workflow does.
- `CHANGELOG.md` is not kept in the repository; the release notes are the changelog. The shared workflow can regenerate
  and commit it (`update-changelog`) once the default branch allows the pipeline to push.
- The packages of the workspace stay at `0.0.0` and are private. When one is published (the viewer, the VS Code
  extension), the release job sets its version from GitVersion before publishing.
- The desktop release (#48) is not part of this; it moved under the Tauri feature (#36).
